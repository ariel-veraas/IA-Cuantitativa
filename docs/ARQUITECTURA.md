# Arquitectura implementada

## Aplicación individual local

El lanzador Go incluye el código y los lectores dentro de un ZIP embebido. En Windows prepara un Python 3.13.15 privado, descargado de python.org y verificado por SHA-256, y arranca `run.py` en modo aislado. La interfaz abre en el navegador y el servidor se vincula únicamente a `127.0.0.1`, con puerto dinámico, comprobación de Host/Origin y token de sesión. No implementa identidad multiusuario ni sirve como host empresarial compartido.

SQLite persiste documentos extraídos, fragmentos, conversaciones, trabajos, capacidades versionadas y movimientos de presupuesto. Un bloqueo de instancia impide dos workers sobre la misma carpeta. Hay un worker y hasta diez trabajos activos en cola. Los checkpoints permiten conservar pasos terminados; un intento externo incierto no se repite automáticamente.

## Decisiones y herramientas

El router combina una capacidad elegida por la persona con selección por palabras y rutas deterministas. Saludos, agradecimientos, cálculos compatibles y comparación textual se resuelven por código. Esto sigue siendo una heurística rápida y sin costo, no comprensión de lenguaje natural: cuando ninguna palabra clave coincide, el sistema usa un valor por defecto razonable (`consultar-documentos` con archivos adjuntos, `asistente` sin ellos) en vez de gastar una llamada al modelo solo para clasificar la intención. Un modelo pequeño interpreta, redacta y devuelve una respuesta JSON. No se confía en una autocalificación numérica de confianza: el estado `needs_help`, los errores de contrato y las reglas de validación determinan la abstención o asistencia externa permitida. Esto no constituye un detector infalible de errores.

La conversación selecciona hasta cuatro documentos, fragmentos por BM25 (ranking léxico por relevancia, con coincidencia de palabra completa — no substring) y una ventana acotada de historial. Cuando se configura un modelo de embeddings local (`embedding_model`, opcional, vacío por defecto), los primeros candidatos de BM25 se reordenan además por similitud semántica: una sola llamada por lotes al motor local por pedido (nunca una llamada por fragmento), así que activarlo no multiplica las llamadas al modelo. Sin ese modelo configurado, el comportamiento es exactamente el BM25 léxico, sin ninguna llamada adicional. Pide `answer`, `needs_help` y referencias `segment_id`; el programa agrega el texto original. Las evaluaciones por rúbrica exigen además citas coincidentes y calculan puntajes con código. Ninguna salida del modelo ejecuta comandos.

El presupuesto local de selección se expresa en caracteres: no equivale al número exacto de tokens. Los idiomas, tablas o instrucciones extensas pueden reducir el contexto efectivo. El reordenamiento semántico es opcional y depende de tener un modelo de embeddings instalado; no hay compresión semántica aprendida propia. Una fuente seleccionada puede ser real y no sostener semánticamente la conclusión.

### Razonamiento adaptativo

Antes de llamar al modelo local, `domain.estimate_complexity` clasifica el pedido (o, en evaluación por rúbrica, la etiqueta del criterio) con una heurística sin costo: palabras que sugieren comparación, causalidad, estrategia o contradicción; dos o más documentos adjuntos; un pedido largo; o más de una pregunta en el mismo mensaje. Si nada de eso aparece, la llamada sigue exactamente como antes: `think`/`enable_thinking` en falso y el presupuesto de salida normal (`max_output_tokens`). Si el pedido parece necesitar razonamiento, la llamada activa el modo de pensamiento extendido del modelo y usa un presupuesto de salida mayor (`reasoning_max_output_tokens`, configurable, acotado para no dejar que el razonamiento crezca sin límite) para dar lugar a los tokens de razonamiento sin truncar la respuesta. El resultado del pedido incluye el campo `reasoning` (visible también en la interfaz) para que quede claro cuándo se usó. Esto es un cambio real de comportamiento del motor, no solo una etiqueta: por diseño es conservador (pocos falsos positivos) porque el propio pensamiento extendido consume más tokens y tiempo, así que activarlo de más sería exactamente el problema que se buscaba evitar. Una excepción deliberada: probar una capacidad propia (`skill_test`) siempre activa razonamiento, sin importar qué diga la heurística sobre el ejemplo — medido con Qwen3 1,7B real, sin esto el modelo ignoraba instrucciones literales cortas que sí seguía correctamente con razonamiento activado.

El prompt de sistema aclara explícitamente que un `document_fragments` vacío no significa que falte información — muchas capacidades (redactar, calcular, una instrucción fija) no necesitan documentos. Sin esta aclaración, medido también con Qwen3 1,7B real, el modelo interpretaba la ausencia de documentos como evidencia faltante y marcaba `needs_help` aunque ya hubiera cumplido el pedido correctamente. Es un ejemplo concreto de por qué este proyecto valida contra un modelo real en vez de asumir que el comportamiento observado con un modelo más grande se sostiene igual en uno más chico.

## Motor y memoria

El administrador descarga una versión fija de Ollama (0.34.2), verifica el SHA-256 publicado por GitHub, extrae rutas seguras y descarga Qwen3 mediante la API nativa. En Windows AMD64 la preparación se controla desde la interfaz. En otros sistemas el código de desarrollo necesita un Ollama existente.

El motor privado utiliza el puerto 11435, un directorio propio, nube de Ollama deshabilitada, un modelo cargado y una solicitud paralela. El perfil elige Qwen3 4B o 1.7B; contexto por defecto 4096 tokens y permanencia de 30 minutos. El razonamiento extendido ya no está desactivado de forma fija: se activa o no según la heurística de arriba, pedido por pedido. Una preparación realiza calentamiento. Esto evita recargar pesos por cada consulta; no elimina los costos de inferencia ni garantiza que todo el modelo entre en VRAM.

El adaptador Ollama usa `/api/chat` con esquema JSON. El adaptador llama.cpp mantiene compatibilidad con `/v1/chat/completions`. La UI permite configurar un motor local existente sin usar el administrador.

## Capacidades

La capacidad de evaluación del repositorio tiene manifiesto, instrucciones y versión. Cada trabajo conserva su configuración. Las capacidades creadas desde la aplicación se versionan en SQLite con instrucciones, ejemplo, frase esperada y un contrato mínimo declarado (`requires_documents`: si la capacidad solo tiene sentido con al menos un archivo adjunto). Ese contrato se comprueba en cada uso real (no en la prueba de ejemplo, que todavía no adjunta archivos): pedir la capacidad sin documentos cuando lo exige devuelve un error claro antes de gastar ninguna llamada. Una prueba local debe terminar correctamente y contener esa frase antes de habilitar la activación manual. Se conserva el historial y es posible reactivar una versión previamente probada. Esta comprobación sigue siendo una única frase de regresión, no múltiples casos de prueba ni un contrato de entrada/salida completo; eso queda pendiente si se necesita más rigor.

### Capacidades que se mejoran a partir de ejemplos

Esto no es entrenamiento ni ajuste de pesos: cada respuesta puede marcarse desde la conversación como "Buena" o "Corregir" (con la respuesta correcta), y esos ejemplos quedan guardados en SQLite (`capability_examples`), asociados a la capacidad usada. Desde Capacidades, "Mejorar con ejemplos" reúne hasta 20 ejemplos recientes —exige al menos una corrección real— y le pide al modelo local que redacte una nueva versión de las instrucciones que resuelva específicamente lo que las correcciones señalan, conservando lo que ya funcionaba. El resultado es una versión más del mismo mecanismo de versionado que ya existía: **tiene que pasar la misma prueba de ejemplo antes de poder activarse**; no se activa sola. Verificado con Qwen3 4B real: a partir de dos correcciones repetidas ("tiene que decir X, no solo Y"), la capacidad propuso instrucciones corregidas, pasó su propia prueba y quedó activable.

Al construir esto se reprodujo en este mismo equipo el problema de "inflación de tokens de razonamiento" que advierte el informe de investigación: con razonamiento activado y sin ninguna otra guía, el modelo podía gastar los 4000 tokens de salida permitidos (el máximo validado) enteramente en "pensar" sin llegar a escribir la respuesta (`done_reason: length`, contenido vacío). Desactivar el razonamiento evitaba el corte pero producía una propuesta fluida que en los hechos no corregía nada. La solución que funcionó de manera reproducible fue una tercera vía: pedirle explícitamente que piense poco ("como mucho 3 o 4 líneas") antes de responder — con eso, terminó de forma natural (`done_reason: stop`) y con la corrección efectivamente aplicada. Este hallazgo se dejó documentado en el propio código (`iq/capabilities.py`), no solo acá.

### Ciclo recursivo acotado y búsqueda web real

La conversación ya no es una única llamada al modelo. Cuando el primer intento local no alcanza (falla la validación o el modelo marca `needs_help`), pasa por hasta dos pasos más, cada uno acotado para no encarecerse solo:

1. **Reconsiderar con más contexto local** (gratis): si hay más contenido del documento disponible del que se usó la primera vez, se amplía el presupuesto de recuperación (hasta el doble, con un techo de 20.000 caracteres) y se vuelve a intentar localmente, esta vez forzando razonamiento extendido. Si no hay más para ofrecer, no se repite la llamada — nunca duplica una llamada idéntica solo por probar de nuevo.
2. **Buscar en la web, solo si hace falta y está permitido** (pago, apagado por defecto): si el pedido tiene pinta de necesitar información actual (`domain.needs_external_info`, una heurística tan barata como la de razonamiento) y la persona habilitó explícitamente "Permitir que busque en la web" en Configuración, se hace una búsqueda real con la herramienta de Google Search de Gemini. El resultado de la búsqueda **no se acepta como respuesta directamente**: se le devuelve al modelo local, gratis, para que reconsidere con esa información y produzca una respuesta validada y citada — la búsqueda solo trae información, nunca responde por su cuenta. Si local no está disponible para reconsiderar, o esa reconsideración también falla, el flujo sigue al paso siguiente.
3. **Escalar a Gemini** (pago): como antes, pero ahora con el contexto comprimido por el modelo local (ver más abajo) en lugar de todo lo que tenía el intento local.

Cada paso pago queda registrado bajo su propio identificador de presupuesto (`conversation-search` para la búsqueda, `conversation` para el escalamiento normal), así que nunca se cobra dos veces por el mismo paso aunque el trabajo se reintente. La búsqueda web es la única función de este documento que **no se verificó contra una cuenta paga real** — el costo que registra se basa en tokens, igual que el resto, pero Google puede cobrar un cargo adicional por búsqueda que esta app no tiene forma de confirmar automáticamente; la interfaz lo advierte explícitamente antes de habilitarla.

### Contexto comprimido antes de pagar

Antes de esta sesión, escalar a Gemini reenviaba exactamente el mismo contexto que ya se le había dado al modelo local. Ahora, antes de escalar, una llamada local adicional y gratuita (`iq/distill.py`) resume en pocas líneas qué se sabe y qué falta, y elige como máximo 6 fragmentos realmente necesarios de los que ya se habían recuperado — nunca agrega fragmentos nuevos que el modelo local no hubiera visto. Si la compresión no está disponible, no aplica (por ejemplo, la capacidad exige citas y no eligió ningún fragmento), o su resultado no es válido, se usa el contexto completo sin comprimir: nunca se manda a pagar con una selección vacía cuando hacían falta fuentes.

No hay entrenamiento, modificación automática de permisos, instalación de plugins arbitrarios ni ejecución de código de capacidades. La evolución de una capacidad queda bajo control de la persona.

## Asistencia externa y gasto

Gemini requiere habilitación global, clave, tarifas verificadas, presupuestos y autorización en el pedido. El adaptador usa `countTokens` y `generateContent`, JSON estructurado y razonamiento desactivado para los modelos permitidos. A diferencia del motor local, esto es intencional y no adaptativo: Gemini solo interviene cuando el motor local ya no pudo resolver el pedido, y un presupuesto de razonamiento variable ahí multiplicaría el costo facturable de una llamada que además todavía no tiene verificación externa propia; mantenerlo apagado prioriza previsibilidad de gasto sobre profundidad de respuesta en ese único paso de escalamiento. El contexto seleccionado se envía también al conteo.

Las reservas usan enteros en microdólares y transacciones SQLite. Se liquidan con el uso comunicado; ante incertidumbre quedan retenidas. Una discrepancia bloquea llamadas posteriores. No hay conciliación de facturas ni límite impuesto a la cuenta de Google. El contenido no se anonimiza automáticamente y no se habilita búsqueda web.

En Windows la clave está protegida con DPAPI; fuera de Windows se guarda en un archivo privado con permisos 0600. Nunca se entrega a la interfaz ni al respaldo SQLite.

## API de integración

Todas las rutas `/api/*` normales están atadas al token de sesión de la interfaz, que rota cada vez que se abre la aplicación — pensado para la pestaña del navegador, no para un programa externo. Para que otro programa instalado en la misma computadora (un script, una automatización, una app propia) pueda mandarle pedidos al cerebro sin re-descubrir un token en cada arranque, existe un segundo mecanismo de autenticación, independiente y estable: una clave de integración (`iqk_...`) generada desde Configuración → Integraciones, guardada en `flags` (tabla SQLite) hasta que se la rota o revoca.

- `GET /api/integration/key`, `POST /api/integration/key/rotate`, `POST /api/integration/key/revoke`: gestión de la clave, autenticada con el token de sesión (solo la interfaz puede generar o ver la clave).
- `POST /api/integration/ask`: autenticada únicamente con el header `X-IQ-Api-Key` (nunca con el token de sesión). Crea una conversación igual que `/api/chat` — mismas reglas de heurística de razonamiento, reintento local con más contexto, búsqueda web opcional y escalamiento comprimido a Gemini — pero, a diferencia de la interfaz (que hace polling desde JavaScript), bloquea la conexión HTTP internamente (sondeo cada 0.3 s) hasta `wait_seconds` (5–120, default 60) y devuelve la respuesta ya resuelta en el mismo request: `answer`, `needs_help`, `provider`, `escalated` (si terminó en Gemini), `reasoning`, `web_search_used`, `evidence`. Si no llega a tiempo, devuelve el estado parcial con `job_id` para consultarlo después.
- `GET /api/integration/status/<job_id>`: mismo formato de respuesta, autenticado con la misma clave, para consultar un pedido que no terminó dentro del `wait_seconds`.

Sigue restringido a loopback (`permitted()`: mismo chequeo de Host/Origin que el resto del servidor) — es integración en la misma máquina, no un servicio expuesto a la red; ese es el límite de diseño deliberado, no un descuido.

## Extracción y límites

TXT/Markdown, DOCX, CSV y XLSX usan lectores acotados; PDF usa pypdf incluido con licencia. Se rechazan archivos demasiado grandes y ZIP con rutas inseguras. No se ejecutan fórmulas ni macros. No hay OCR ni aislamiento del lector en un proceso de seguridad. Los originales no se almacenan ni modifican.

El backup utiliza la API de copia consistente de SQLite. La restauración se realiza con la aplicación cerrada; no tiene interfaz. El borrado de documentos no elimina automáticamente su contenido histórico en resultados. Las capacidades empresariales compartidas, conectores y políticas administradas no forman parte del alcance implementado.
